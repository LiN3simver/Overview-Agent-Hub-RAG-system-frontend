這裡講的是「東西怎麼接的」：六個服務各自負責什麼、一句問話送出去之後經過哪些手、 系統怎麼自己決定要不要用工具與問別人。 想知道「我能問什麼」請看左邊那個分頁。

一、六個服務怎麼接

五個 agent 是五個各自獨立跑起來的服務，彼此不共用資料庫、也不共用程式； Hub 是第六個，它自己沒有語料，負責統一前端、保管對話、轉發訊息。 箭頭方向就是呼叫方向。 8D 客訴單 Agent 有兩個上游：產品估價要它評報價前的品質風險， Bom 要它查換料前這顆料的客訴史。

實線 = agent 之間的委派方向（單向，不會繞回來）；虛線 = Hub 的轉發與共用的 LLM。 狀態燈是即時讀 /hub/agents 畫的。 8D 客訴單 Agent 有兩條實線進來（產品估價與 Bom 各一條）而自己沒有下游 —— 所以不管誰問它，都不可能繞回上游。ISO 文件 Agent 是獨立節點，沒有任何連線。

為什麼要多 Hub 這一層

  • agent 的埠都不對外開。瀏覽器認得到的只有 Hub 一個位址， 連卡片上的 PDF 連結都是指回 Hub、再由它轉打進真正持有檔案的那個 agent。
  • 對話需要一個家。對話集中存在 Hub，agent 一律無狀態， 每一輪由 Hub 把歷史帶過去 —— 新的 agent 一行對話程式都不用寫， 同一段對話也能換另一個 agent 接著回答。
  • 不必為了前端去改在跑的服務。瀏覽器從 Hub 直接打其他埠是跨來源請求， 每個 app 都得改設定；統一由 Hub 轉發就一個字都不用動。
  • 「某個 agent 沒開」在一個地方講完。不必每個頁面各自轉圈。
  • 加一個 agent 不用改前端。拓撲、名片、範例問句全部讀 registry 與 /a2a/card，新增 agent 時前端一個字都不用動。

二、一則問答走過的路

送出問題後畫面上會依序出現：檢索中… → 卡片 →（有跑工具時）軌跡 → 逐字的回答。 那個順序不是巧合，是後端固定的事件順序：

LLM 那一段（右邊兩條虛線）掛掉時，左邊那條 results 已經送出去了 —— 這是刻意的順序。

事件意思
meta這一輪由誰回答、跑的是哪一種模式
results檢索結果 —— 一定在問 LLM 之前送出，LLM 掛掉時至少資料已經到畫面上了
trace工具／委派軌跡：哪一步、呼叫誰、參數、成功失敗、幾毫秒
delta回答逐字送達
errorLLM 或下游出狀況時才有，附帶「該怎麼辦」
done這一輪結束
按「暫停」是真的停。暫停會切斷瀏覽器到 Hub 的連線，Hub 偵測到之後主動關掉 它對 agent 的連線，agent 再關掉打去 LLM 的串流 —— 三段一路收掉，不是畫面停了、 後面還在燒 token。

三、系統怎麼自己決定要用工具、要不要問別人

「用自己的工具」「問其他助理」「只列資料」這三件事不需要使用者勾選， 由系統在送出的當下自己判，判準如下。

用自己的工具

有工具就一定開
自己的工具 ✓ 下游 ✗

資料完全不離開這個 agent，沒有需要事先同意的事。模型自己決定要查什麼、 查幾次。畫面標示「· 只用自己的工具」。

問其他助理

有別人可問才開
自己的工具 ✓ 下游 ✓

這個 agent 有下游、而且下游至少有一個開著時才掛上他們的工具。 開著不等於一定會問 —— 真正的判斷在下一段。畫面標示「· 需要時會問其他助理」。

只列資料

LLM 連不上時自動
摘要 ✗ 卡片 ✓

LLM 打不通時自動跳過它，回答停在 results 那一步：卡片照樣查得到， 只是沒有人幫你寫成一段話。前端與 Hub 各判一次，程式化呼叫也一樣。

「只有自己真的答不出來才問別人」是模型當場判的，不是勾一個框事先猜的。 委派迴圈的 system 明寫著：自己手上的檢索結果或自己的工具足以回答時， 直接回答、不要呼叫任何下游；只有缺的那一塊自己真的沒有時才委派， 而且只問缺的那一塊，不要把整題轉包出去。 理由很實際 —— 多問一輪要多花好幾秒與好幾倍 token，答案還可能被無關的資料帶偏。
沒有別人可問的時候，它不會假裝問過誰。 這個 agent 沒有下游、或下游全部沒開機時，模型的工具清單裡根本不會出現別人的工具， 連下游的名片都不寫進去；就算它硬湊出一個像下游工具的名字，執行前也會被擋掉。 這種時候 system 會改成「你只有自己的工具」，缺資料就直說是哪一塊缺， 不會用猜的料號或數字補位。

四、委派迴圈裡實際發生什麼

這個 agent 有工具（或有下游可問）時，回答不再是「檢索一次就寫答案」，而是一個迴圈： 模型自己決定要不要查、查什麼，拿到結果再決定下一步。

最後那一格是「畫面一定會有東西」的保證：資料都查到了，不能讓你拿到一片空白。

兩種呼叫下游的方式

方式什麼時候用
<agent>__<工具> 知道要哪一筆資料，直接帶參數去拿（例如「這顆料有幾張客訴單」）
ask_<agent> 問題屬於對方專業，但不確定要用它哪一支工具 —— 整句話丟過去讓它自己判斷， 它還可以再往下問它自己的下游

第二種不是多餘的。有的 agent 自己的工具還沒就緒（會誠實回「尚未可用」， 因此不會掛給模型），這時候只剩「跟它講話」這條路 —— 而它有下游， 所以它答得出來。能對話本身就是一種能力。

兩件刻意這樣做的事

  • 圖是單向的。只掛得到自己的下游，往回呼叫會被擋掉並收到「不是你的下游」 的說明。這是防環最便宜的做法：不可能繞成 A→B→A。
  • 少一塊也要照樣回答，不是拋錯。下游沒開就回「未啟動」；工具沒就緒就 不掛給模型（掛了它會呼叫、失敗、然後開始猜）；下游自己的限制（覆蓋率多少、 哪個數字不可信）會被抄進上游的指示裡。例如 Bom Agent 的下游都沒開時， 回答會像這樣（示意）：
結論：目前查不到這顆料的相似料號與客訴紀錄。
1. 相似搜尋建議 Agent 未啟動 —— 它的工具不在我的清單中。
2. 8D 客訴單 Agent 未啟動 —— 無法確認這顆料的客訴史。
以下只根據我自己查到的現行 BOM 回答。

沒有掛掉，也沒有編一個答案出來。這是設計目標，不是巧合。

五、狀態燈是怎麼判的

● 就緒 — 語料與依賴都在，可以正常回答 ● 尚未就緒 — 依賴不在或功能未實作，會照實說 ● 未啟動 — 那個服務沒開
  • 每個 agent 自己回報狀態，Hub 只是把名片收齊了畫成燈。
  • 檢查有硬期限（2.5 秒）。資料庫容器停掉時，連線池要卡滿 30 秒才會放棄 —— 沒有期限的話，整個介面會在資料庫掛掉時轉半分鐘，而且上游 agent 會直接判它離線。 逾時就先回上一次的結果並標明是舊的，背景那條檢查讓它自己跑完。
  • 同一時間只派一次檢查。資料庫卡住時大家一直重新整理，如果每次都多派一條 去問，會越積越多、把資料庫壓得更慘；所以後到的人一律等同一次的結果。 舊結果最多沿用一分鐘，太舊就不再當成現況；一次檢查卡超過 30 秒直接判「尚未就緒」。
  • 忙不等於壞。每個 agent 同時只查幾筆，滿了會直接回「目前已經滿了，請等幾秒再送一次」， 而不是讓每個人都慢慢等。看到這句話代表服務好好的、只是忙，不要去重開它。
  • 結果會快取十幾秒。剛把某個服務開起來、燈還沒變，重新整理一下就好。
  • 後端還有一個「降級」狀態，畫面上一律當成就緒。它代表的是背景排程沒跑完、 某個能力還沒實作這類「服務其實答得動」的事 —— 對著一個答得出來的 agent 說它降級， 只會讓人以為現在不能用，所以那個字不出現在任何畫面上。真的答不出來時， 狀態會是「尚未就緒」或「未啟動」，那兩個才會講。

六、卡片上的資料規則

  • 卡片裡 空白 跟 0 是兩件事：欄位沒填顯示「未填」，欄位填了 0 就顯示 0。 某些庫只有極少數單子有成本明細，把「未填」畫成 0 會讓人以為成本真的是零 —— 後端一路保持兩者可分，前端才畫得出來。 客訴單上的「退回數／不良數」也是同一條規則：0 是真的一件不良都沒有， 空白是那張單沒填，兩者合併掉會讓人以為這批貨沒問題。
  • 「沒查到」與「沒發生」是兩件事，卡片與答案都要分開講。 客訴單語料有起訖範圍，所以它講的是「這份語料裡查不到這顆料的客訴」， 不會講成「這顆料沒出過事」—— 上游會拿這句話去決定報價。 同理，客訴單上「是否成立」有近一成是還沒判定，那不是「不成立」。
  • 卡片上的 raw 一定是原封不動的原始列。正規化只是為了畫得出通用卡片， 不是拿來取代原始資料。
  • 「帶去問」的按鈕只會出現在這一輪真的問到的 agent 上， 不會列出所有活著的 agent 誘導點擊。
  • 卡片上如果有「資料來源」連結，點開是原始附件（例如工程圖 PDF、成本分析的掃描件）。 那個連結一律指回 Hub 再轉打進去 —— 因為持有檔案的 agent 不對外開埠。 數字對不對得起來，自己開原檔核對。

七、對話存在哪裡、算誰的

  • 對話集中存在 Hub（SQLite 資料庫，每天自動備份一份），每個 agent 完全無狀態。 每一輪由 Hub 把歷史帶過去，所以同一段對話可以換另一個 agent 接著回答。
  • 每一輪都會留下來，包括出錯、超過時間、或你按了暫停的那一輪 —— 已經查到的卡片與已經講出來的字都在，重新打開對話看得到。
  • 一題最多等三分鐘。時間到了會停止產生並說明原因，上面已經查到的資料仍然有效； 可以把問題縮小（指定編號、料號或時間範圍）再問一次。
  • 清單、讀取、刪除只認你自己的那一份：第一次開頁面時 Hub 會發一個瀏覽器 自動帶的識別碼。這不是登入 —— 它擋的是「不小心看到或刪到別人的對話」， 擋不住刻意冒用的呼叫端。要擋那個得先有帳號系統。
  • 對話標題預設取問句前 40 字，改過之後不會被後面的訊息蓋回去。

八、同一套東西的兩種部署

  • 本機開發：六個服務各自啟動、各自對外開埠。有資料庫容器的是 相似搜尋與產品估價；Bom 與 8D 客訴單不落地，直接查來源系統。
  • 伺服器：整組跑在同一個內部網路裡，只有 Hub 對外， agent 的埠一個都不開 —— 所以附件連結才必須走 Hub 代理那條路。
  • 資料更新（PLM 主檔、工程圖）是排程做的，跟前端無關； 排程沒開的話，你看到的就是上一次匯入那一刻的快照。
